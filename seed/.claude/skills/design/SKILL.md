# design

## 1. 質問(1往復で)
曖昧な点を **最大4問、選択肢つきで一度にまとめて** 聞く。観点: 目的 / やらないこと / 入出力 / エラー時の挙動 / 既存への影響 / データ移行。
答えから明らかなことは聞かない。足りなければもう1往復だけ。

## 2. 設計書(plan mode の計画をこの形で書く)
承認後、同じ内容を `docs/design/YYYYMMDD-<topic>.md` に保存する(plan と別に書き直さない)。

```markdown
# <機能名>
## 目的 / やらないこと
## 受け入れ条件
- [ ] AC1: <条件。検証できる形で> → 確認: <テスト名 or verify-app の手順>
## 方針(採用案 / 却下案と理由を1行ずつ)
## 失敗しそうな点(3行まで)
## ロールバック(DB・データ・外部契約に触れる時のみ)
```
戻しにくい判断を含むなら `docs/adr/NNNN-<title>.md` も書く(`docs/adr/TEMPLATE.md`)。

## 3. 実装
- 受け入れ条件のテストを先に書き、ユーザーに見せてから実装する。
- 実装中に設計を変えるなら、設計書を先に直して一言報告する。

## 4. 仕様照合(実装後に1回)
サブエージェントを1体だけ起動し、次をそのまま渡す(パスを差し替える):

> `docs/design/<file>.md` の受け入れ条件と「やらないこと」に照らして、`git diff <base>` の変更をレビューせよ。各受け入れ条件が実装され、確認方法のテストまたは手順が存在するかを1行ずつ判定し、正しさに影響する欠落・矛盾だけを報告せよ。スタイル・命名・好みの指摘はしない。

- 指摘を直したら、再レビューは **新しい差分だけ** を対象にする。合計3ラウンドで打ち切り、残りはユーザーに報告。
- 最後に verify-app で受け入れ条件を実際に確かめ、設計書のチェックを埋める。
