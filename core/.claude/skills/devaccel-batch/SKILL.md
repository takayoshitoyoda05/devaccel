# devaccel-batch

## 自動で使うかの判断(ユーザーに確認しない)
次をすべて満たすときファンアウトにする。1 つでも外れたら普通に 1 セッションで順に実装する(その後 devaccel-pr)。
- **独立した作業が 4 件以上**(3 件以下は逐次のほうが速い・安い。実測 D14/D17)。
- 各件が **別のファイル** を作る・変える(同じファイルを触る件どうしは 1 件にまとめる)。
- 各件が S〜M(L = 3 ファイル超・設計判断あり・認証/DB/削除/秘密情報 は並列にしない。design スキル)。
- 仕様が依頼文から書き下せる(書けない件はユーザーに質問してから)。
- 作業ツリーがきれい(未コミットの変更がある・main 以外の作業ブランチにいるなら、先に devaccel-pr で片付けるか逐次にする)。

## 設計書(依頼がざっくりしているとき。番号付きの仕様なら書かない)
`docs/design/YYYYMMDD-<短い名前>.md` に Write する。これがそのまま単位への指示書になり、PR にも入る(人は差分ではなくこれと証拠を見る)。形:
- 冒頭(1. より前): 目的・やらないこと・全件共通の前提(使う既存の型、標準ライブラリだけ、既存ファイルは変えない など)。
- 件ごとに `1.` `2.` …: ファイルとテストファイル(`` `src/...` ``)/ 関数・クラスの名前と型 / 入力 → 出力の具体例(端: 空・0・月末・不正な形式・重複・全角、と出す例外)/ 結果の並び順と同点 / 受け入れ条件(箇条書き。チェックボックス `- [ ]` は使わない)。
- 依頼から決められない点は、妥当な既定を選んで「(既定)」と書く。L 規模なら設計書を見せて承認を待つ(design スキル)。それ以外は待たずに進む。
書いたら 2 の依頼ファイルを `docs/design/<その名前>.md` にする。

## 手順(ファンアウト)
1. **ユーザーの依頼文が既に件ごとの仕様(`1.` `2.` … と番号付き)なら、何も書かずに** 2 で依頼ファイルを `.devaccel/prompt.md` にする(実行の瞬間にガードがユーザーの依頼文をそのまま書き出す。事前に確認・作成しない。打ち直しの時間とコストが要らない)。番号付きでなければ、`.claude/skills/devaccel-batch/reference.md` の書き方を読んでから、依頼を `.devaccel/tasks.md` に **毎回 Write で上書きする**(前回のファイルが残っていても読まずに書き直す)。依頼文が既に件ごとの仕様になっていれば、そのまま写す(言い換え・要約しない)。親はコードを読み込みすぎない: 名前・型・ファイルの場所を確かめる程度にとどめる(中身は単位が読み、名指しした小さなファイルは自動で埋め込まれる。親の読み込みはそのままコストになる)。
2. 単独のコマンドで実行する(パイプ・リダイレクト・`&&` を付けない。出力は数行。Bash の timeout は 600000。サンドボックスの外で動くよう設定済み。単位はそれぞれサンドボックス内):
   `python3 .claude/hooks/devaccel_batch.py .devaccel/prompt.md --branch batch/<短い名前>`(または `docs/design/<名前>.md`・`.devaccel/tasks.md`)
   - `error:` で止まったら(作業ツリーが汚い・ブランチ名など)直してから再実行。`--dry-run` は何も動かさずに点検だけする。
3. 短く報告する(3〜5 行。単位ごとの詳細は PR 本文とログにある): PR の URL とラベル、`units: X/Y ok`、外れた件と理由(`check fail`・`touches protected files` など)。外れた件は、ユーザーに伝えたうえで逐次で実装し直してよい(手で取り繕って ok に見せない)。マージは人。
