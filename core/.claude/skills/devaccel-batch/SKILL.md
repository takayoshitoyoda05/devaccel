# devaccel-batch

## 自動で使うかの判断(ユーザーに確認しない)
次をすべて満たすときファンアウトにする。1 つでも外れたら普通に 1 セッションで順に実装する(その後 devaccel-pr)。
- **独立した作業が 4 件以上**(3 件以下は逐次のほうが速い・安い。実測 D14/D17)。
- 各件が **別のファイル** を作る・変える(同じファイルを触る件どうしは 1 件にまとめる)。
- 各件が S〜M(L = 3 ファイル超・設計判断あり・認証/DB/削除/秘密情報 は並列にしない。design スキル)。
- 仕様が依頼文から書き下せる(書けない件はユーザーに質問してから)。
- 作業ツリーがきれい(未コミットの変更がある・main 以外の作業ブランチにいるなら、先に devaccel-pr で片付けるか逐次にする)。

## 手順(ファンアウト)
1. 依頼を `.devaccel/tasks.md` に Write する(書き方は下)。親はコードを読み込みすぎない: 名前・型・ファイルの場所を確かめる程度にとどめる(中身は単位が読み、名指しした小さなファイルは自動で埋め込まれる。親の読み込みはそのままコストになる)。
2. 単独のコマンドで実行する(Bash の timeout は 600000。サンドボックスの外で動くよう設定済み。単位はそれぞれサンドボックス内):
   `python3 .claude/hooks/devaccel_batch.py .devaccel/tasks.md --branch batch/<短い名前>`
   - `error:` で止まったら(作業ツリーが汚い・ブランチ名など)直してから再実行。`--dry-run` は何も動かさずに点検だけする。
3. 出力をそのまま報告する: PR の URL とラベル、`units: X/Y ok`、外れた件と理由(`check fail`・`touches protected files` など)。外れた件は、ユーザーに伝えたうえで逐次で実装し直してよい(手で取り繕って ok に見せない)。マージは人。

### 依頼ファイルの書き方(単位は haiku。往復が減るほど速く安い)
時間は最も遅い単位で決まり、遅い単位は「書く → テストが落ちる → 直す」の往復が多い。仕様の曖昧さが往復の主因なので、各件に次を書く:
- **ファイル**: 作る・変えるファイルとテストファイルを `` `src/...` `` の形で(既存の 8 KB 以下のファイルは単位への指示に自動で埋め込まれる)。
- **型と名前**: 関数・クラスの名前と引数・戻り値の型。使う既存の型(例 `core.py` の `Expense`)。
- **境界の例**: 入力 → 出力の具体例を 2〜4 個。特に端(空、0、月末、不正な形式)と、どの例外を出すか。
- **順序と同点**: 結果の並び順、同点のときの扱い。
- **やらないこと**: 触らないファイル、範囲外の機能(CLI 組み込みなど)。
- 冒頭(1. より前)に全件共通の前提を書く(各件に繰り返さない)。
各件が別のファイルを編集するように分ける(重なると統合で衝突し、その件は外される)。
実行すると、ファイルやテストの名指しが無い件には警告が出る(実行は止めない)。

## 会話の中での並列(サブエージェント。ファンアウトが使えない環境か、ユーザーが望むときだけ)
ファンアウトより遅い(D14)。

親の手数がそのまま時間になる。git の下準備や結果の再確認で手を増やさない:
1. **親は薄く**: 親はコードを読まない(読むのは単位)。依頼文を単位ごとに分け、各単位への指示は **その件の文面そのまま(+ 共通の前提があれば 1 行)だけ**。規則・手順・リポジトリの説明は書かない(`devaccel-unit` の定義にある)。指示文が長いと、書き出す時間のぶん単位の起動が順にずれる(実測: 1 件 2,000 字で約 5 秒ずつ)。README・docs を変えるなら担当を 1 単位に決める。
2. Agent ツールで `devaccel-unit` を **単位の数だけ同じメッセージで** 起動する。各単位の返事の `branch:` を控える(返事の要約以外は読み込まない)。
3. `.devaccel/ship.md` に Write(1 行目 = 題名、以降 = 単位ごとに 1 行の確認メモ)し、単独のコマンドで:
   `python3 .claude/hooks/devaccel_ship.py --file .devaccel/ship.md --branch batch/<名前> --units <branch1> <branch2> ...`
   - 作業ブランチの作成(origin/<base> から)→ 単位を `--no-ff` で統合(衝突した単位は外して報告)→ base の check.sh を 1 回 → push → PR 1 本。
4. ship の出力(URL・ラベル・外した単位・失敗した段)をそのまま報告する。`needs-human` や検査失敗はユーザーに伝える(親が手で直して取り繕わない)。マージは人。
