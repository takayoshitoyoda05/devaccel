## 0. 総評

### 0.1 根拠に照らして妥当な点(変えなくてよい)

| 設計の要素 | 支える根拠 |
|---|---|
| 自作エージェント 0 個で始める | 公式は「同じタスクを委譲しても答えは良くならない」とし、Anthropic 自身のリポジトリも agents なし(公式 ◎、実測 ○。サーベイ 0.4) |
| 検証の本体を Claude 非依存の `scripts/check.sh` にし、CI でも同じものを回す | 公式は「決定的な検査 + 人の最終承認」を最後の砦とする。`-p` は将来 `--bare` が既定になりフックを飛ばす予定なので、CI がフックに依存しない設計は正しい(公式 ○ https://code.claude.com/docs/en/headless) |
| フックは 2 本、python3 標準ライブラリのみ | 公式は「例外ゼロの規則だけをフックに。40 個あれば大半は好み」(公式 ◎)。前回提案の実測で `python3` 起動は 0.009 秒 |
| setup / tune を `disable-model-invocation` | 説明文が常駐しない(公式 ◎) |
| off / observe / enforce と spike ブランチのスキップ | 既知資料と一致。公式も「フックは時々誤発火する」と明記(公式 ◎) |
| curl\|bash をやめ、タグ固定の clone + install.sh | 自動更新は任意コード実行と同じ(公式 ○ https://code.claude.com/docs/en/plugins/security)。plugin は常駐層と permissions を運べず、project scope の有効化だけではインストールされない(公式 ◎)。「他の人は clone するだけ」を満たすにはリポジトリ内コミットが最も確実 |
| update.sh がハッシュで手編集を検出し、project 層に触らない | spec-kit、`npx skills` と同じ型(実測 ○)。`gh skill update` のようにローカル追加を消す事故を避けられる(実測 ◎ https://github.com/cli/cli/issues/14647) |
| L だけ設計書、人の承認は計画段階 | 仕様先行は規模の閾値を超えた時だけ得(実測 ○)。計画の却下率 39% 対 個別権限 3%(公式(内部データ)○) |
| 受け入れ条件に確認方法を付ける | テストの質が律速(人が書いたテスト 94.3% 対 LLM 68.0%、実測 ○ https://arxiv.org/abs/2510.23761) |

### 0.2 最も大きな懸念(要約)

1. **Stop ゲートの解除条件が二重で、かつ「理由を書かせて通す」は検証されない自己申告に頼る。**
2. **所有権の境界が 2 か所で曖昧**(settings.json の hooks マージ、project 層に置かれた check.sh にロジックが溜まる)。更新の伝播とカスタマイズ保持の両方を損なう。
3. **L3 の「/code-review を受け入れ条件の照合に限定」は、組み込み `/code-review` では実現できない。**
4. **Stop ゲートの速度予算と pyright の「変更ファイルのみ」が、速さと正確さの両方で穴になる。**
5. **tune は放っておくと「追加」に偏る。** 追加先の優先順位と削除の契機が設計に無い。

### 1.1 トークン削減

| # | 弱点 | 根拠 | 修正案 |

| K5 | L3 のレビューは新規サブエージェントで、CLAUDE.md を継承して起動する。常駐が小さいほど安いが、頻度の上限が設計に無い | サブエージェントのコストは「起動時コンテキスト × 体数」(実測 ○)。Anthropic は 3 ラウンドで打ち切り、以降は新しい差分のみ(公式(内部データ)◎) | レビューは 1 タスク 1 回を既定、再レビューは新しい差分だけ、と design スキルに書く |

### 1.2 正確さ

| # | 弱点 | 根拠 | 修正案 |
|---|---|---|---|
| A1 | 「3 ラウンドで停止」と「同一セッションで 2 回ブロックしたら理由を書かせて通す」が両立しない。どちらが先に効くか不明 | ハーネス側の上限は「ツール呼び出しを挟まない連続 8 回」で、ツールを呼ぶとリセットされる(公式 ◎ / ○ https://code.claude.com/docs/en/hooks#stop)。つまり独自の回数管理は必要だが、規則は 1 本でよい | 規則を 1 本にする。例: 「同じ段が N 回(既定 3)連続で落ちたら解除」。回数は `session_id` ごとの状態ファイルで数える |
| A2 | 解除時に「理由を書かせて通す」は、検証されない自己申告を通行証にしている | 不正確な自己報告は不整合の 22.6%(実測 ○ https://arxiv.org/abs/2605.29442)。LLM の審判は自信のある文面に騙される(実測 ○)。Opus 5.5 で最多の検出挙動は「未検証の推論を事実として述べる」(公式(内部データ)○)。一方「人にエスカレーションする」出口はテスト不正を 54%→9% に下げた(実測 ○ https://arxiv.org/abs/2510.20270) | 解除は「通す」ではなく「止めて人に報告する」と位置づける。解除時にフックが (1) 未解決の失敗を記録ファイルに残し、(2) ユーザー向けに「検査未通過のまま終了」と表示し(`systemMessage`)、(3) Claude には「失敗した段と出力を示して判断を仰げ」とだけ返す。理由の作文は求めない |
| A3 | 既定 observe のまま昇格しないと、L1 は何も強制しない | 公式は「必ず起きてほしいことはフックに」(公式 ◎)。前回提案には昇格条件(発火 10 回以上・誤検知 0)があったが、今回の設計案には無い | 昇格条件を project.toml に書き、doctor.sh が「条件を満たしたのに observe のまま」を指摘する。段ごとにモードを分けるとさらに安全: 整形と自動修正可能な lint は最初から自動修正(ブロックしない)、型とテストだけ observe→enforce |
| A4 | pyright を変更ファイルだけにかけると、呼び出し側の型エラーを見逃す | 型エラーはファイルをまたぐ(シグネチャ変更で未変更ファイルが壊れる)。この見逃しは CI(L4)まで出ない | setup 時にプロジェクト全体の pyright 時間を測り、予算内(例: 10 秒)なら fast でも全体にかける。超える場合だけ変更ファイルに絞り、その旨を project.toml に記録する。補助として公式の pyright LSP プラグインは編集直後に型エラーを返す(公式 ◎ https://code.claude.com/docs/en/costs)。ただし各マシンで導入が要り、クラウドでは動かない(公式 ○)ので必須にはしない |
| A5 | 不正検知の「警告」は、誤検知が多い項目(assert の減少)を含み、相手も Claude | assert 数は正当なリファクタで減る。公式は「フックは時々誤発火する」(公式 ◎)。監視の告知は研究用モデルで隠れたハックを 4%→19% に増やした(公式(内部データ)○。現行モデルで同じかは未確認) | 2 つに分ける。(a) 検査そのものの改変(check.sh、フック、CI、project.toml のゲート項目)は、事後検知ではなく permissions の `ask` で事前に止める。ask / deny は auto mode より前に効き、プロセスも起動しない(公式 ◎)。(b) テストの弱体化(テストファイル削除、skip / xfail 追加)は Claude への警告ではなく人向けの表示にし、L3 の照合項目にも入れる。assert の数は外す |
| A6 | project 層の check.sh は Claude が書き換えられる。ゲートが自分で緩められる | 既知資料「変更が自分のチェックを書き換えられない」。前回提案はプラグインキャッシュに置いて守っていたが、リポジトリ内コミットに変えたのでこの保護が消えた | A5(a) の `ask` に加え、チーム利用では CODEOWNERS とブランチ保護で check.sh / .claude/ / CI を守る(公式も「最後の決定権はブランチ保護と人」◎) |
| A7 | L3 は「/code-review を受け入れ条件の照合に限定」とあるが、組み込み `/code-review` の観点は外から絞れない | ローカル `/code-review` は REVIEW.md を読まず、CLAUDE.md を読む(公式 ○ https://code.claude.com/docs/en/code-review-local)。公式が仕様照合に勧めるのは `/code-review` ではなく自分で書くプロンプト: "use a subagent to review the ... diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style"(公式 ◎ https://code.claude.com/docs/en/best-practices) | L3 を 2 つに分ける。仕様照合は、design スキルの最終手順に上の定型プロンプト(設計書のパスを差し込む)を置く。自作エージェント定義は不要。一般的なバグ探しは `/code-review low` を任意で。「見逃しが出たら reviewer を 1 個足す」は、公式の例(tools: Read, Grep, Glob の 1 ファイル)がそのまま使える |
| A8 | S / M / L の判定がモデル任せで、過小判定を止める仕組みが無い(前回提案 §9 の既知リスク) | CLAUDE.md は指針で、従うかは Claude の判断(公式 ◎) | 事後の決定的な判定を足す。stop_gate が差分の規模と `risky_paths` を見て、閾値を超えたら 1 セッション 1 回だけ「L 相当。設計書と仕様照合を検討」と返す。常駐 0 で、発火時だけ 1 行 |
| A9 | verify スキルは setup 時に Claude が生成する | 自己生成スキルは効果なし、LLM 生成のコンテキストファイルは成功率を下げる(実測 ○。SkillsBench の該当数値は最新版の要旨では未確認) | 生成後に setup が実際に 1 回実行して通ることを確かめ、人が差分を読んでからコミットする。中身は起動コマンドと落とし穴に限る(公式: スキルは「落とし穴を先に、手順より目的」○) |
| A10 | Stop フックは質問で終わるターンでも走る。作業途中の状態で落ちてブロックする | Stop は毎ターン末に発火する(公式)。誤検知は回避行動とトークン浪費を生む(実測 ○ https://arxiv.org/abs/2608.00101) | 完全には防げない。observe 期間のログに「ブロック後、次のユーザー発話で作業が続いたか」を残し、誤検知率として tune の入力にする。高ければテスト段だけ「変更が 2 ターン続いて安定したら走らせる」等を検討(未検証) |
| A11 | テスト通過への過適合 | テストを通るパッチの 22〜33% が隠しテストで落ちる(実測 ○)。フィードバックループは不正を増やしうる(実測 ○) | L では受け入れ条件のテストを実装より先に書き、人が承認する(設計案の「確認方法つき受け入れ条件」をテストまで具体化)。L2 の実動作確認を省かない |

### 1.3 高速開発

| # | 弱点 | 根拠 | 修正案 |
|---|---|---|---|
| S1 | 「差分がなければ即終了」だけだと、作業ツリーが汚れている間は質問だけのターンでも毎回フルに走る | 前回提案は「前回 PASS 時から作業ツリーが変わっていなければ即終了」(署名スキップ)だった。今回の記述はそれより弱く読める | 署名スキップを明記する(追跡ファイルの差分 + 未追跡ファイルのハッシュが前回 PASS と同じなら終了)。`.py` と設定以外だけが変わった場合(docs など)も終了 |

| S3 | 整形で「ブロック」すると 1 ラウンド無駄になる | 再試行ループは計算を増やす(実測 ○) | 整形と `ruff check --fix` は check.sh fast の中で黙って直す。直せなかったものだけ失敗にする |
| S4 | L の「曖昧な点を 1 問ずつ質問」は往復が多い | 公式のインタビューは選択式の質問をまとめて出す(公式 ◎ https://code.claude.com/docs/en/best-practices)。仕様先行は時間 +7〜26 分(実測 ○) | 質問は 1 回にまとめ(上限 3〜4 問、選択式)、既定は 1 往復。足りなければ追加 |
| S5 | plan mode の計画ファイルと docs/design/*.md が二重になる | plan mode の計画は compaction 後に再注入される(公式 ◎)。同じ内容を 2 か所に書くと時間とトークンが倍 | 成果物を 1 つにする。plan mode の出力をそのまま設計書の形(目的 / やらないこと / 受け入れ条件 …)にし、承認後に docs/design/ へ保存する |
| S6 | 並列(worktree)への備えが無い | worktree は新規チェックアウトで `.env` と依存が無い(公式 ◎)。worktree は別ディレクトリなのでキャッシュも別(公式 ◎) | プリセットに `.worktreeinclude`(`.env` など)を入れ、CLAUDE.md に `uv sync` の 1 行。stop_gate の状態ファイルは worktree ごと(gitignore 済みのディレクトリ)に置く |
| S7 | auto mode を使わない協業者は権限プロンプトが多い | `permissions.defaultMode` の auto は project 設定から指定できない。`allow` は信頼承認後に有効(公式 ○) | settings.json の allow に `uv run pytest *`、`uv run ruff *`、`uv run pyright *`、`scripts/check.sh *` を入れる。allow は `*` の位置と空白に注意(公式 ○ https://code.claude.com/docs/en/permissions) |
| S8 | guard.py は Bash のたびにプロセスを起動する | フックの `if` はプロセス起動自体を避ける(公式 ◎)。auto mode は force push などを既に止め、deny / ask はそれより前に効く(公式 ◎) | 宣言で書けるもの(`sudo`、force push、`.env` の読み書き)は deny / ask に移す。guard.py は規則で書けない判定(`rm -rf` の対象、`git add -A`)だけにし、`if` で対象コマンドの時だけ起動する(1 ハンドラ 1 規則なので、対象ごとにエントリを分ける) |

### 1.4 多様なプロジェクトへの対応と流動性

| # | 弱点 | 根拠 | 修正案 |
|---|---|---|---|
| F1 | check.sh が project 層(生成後は自由に変更)だと、変更ファイルの算出・時間計測・出力整形といったロジックがそこに溜まり、テンプレートの改良が届かなくなる | コピー方式のドリフトは既存テンプレート共通の失敗(実測 ○。12 プロジェクトで版がばらばらになった報告は自己申告) | check.sh は「コマンドを並べるだけ」に保つ(fast / full で各 5 行程度)。賢い部分(署名スキップ、打ち切り、落ちた段の切り出し、ログ)はすべて core の stop_gate.py に置く。こうすれば project 層は本当に自由に変えてよく、core は更新で良くなる |
| F2 | 「settings.json は hooks キーだけをマージ」は壊れやすい。JSON の機械編集、重複、キー消失 | Claude Code 自身の settings 書き込みが未知キーを消したという報告がある(自己申告 ○ https://github.com/anthropics/claude-code/issues/88113)。plugin 変換でも「元を残すと同じフックが二重に動く」(公式 ○) | マージしない。フックのエントリは不変の 2 行(固定パスの `python3 "$CLAUDE_PROJECT_DIR"/.claude/hooks/…`)にし、install 時に 1 回だけ書く。update.sh は settings.json に触らず、doctor.sh が「2 行があるか」を点検して無ければ貼る断片を表示する。配線を変える版では移行手順を表示する |
| F3 | `.new` ファイルは放置されやすく、解決手順も無い | spec-kit は手編集を検出して止まる。OpenSpec は生成物を編集不可と宣言する(実測 ○) | core を「編集しない層」と宣言し(ファイル冒頭に 1 行、調整点は project.toml)、手編集があれば update は止まって差分を表示する。どうしても統合したい場合に限り、テンプレートの clone に旧タグが残っているので `git merge-file` で 3 方向マージができる(lock に導入時のタグを記録しておく)。`.new` は置かない |
| F4 | project.toml の読み取りに `tomllib` を使うと Python 3.11 以上が要る | `tomllib` は 3.11 から標準(Python 公式)。Ubuntu 22.04 の既定は 3.10 | 「他の人や CI」があるので、doctor.sh と install.sh で 3.11 以上を点検するか、設定を JSON にする。フックは古い Python でも黙って落ちず、明示的に知らせる |
| F5 | プリセットの「組み合わせ」は、言語 × フレームワーク × ツールの行列にすると爆発する | 公開テンプレートの主流は自動検出ではなく選択導入 + リポジトリごとの 1 回の setup(実測 ○)。Python 中心という決定事項 | プリセットを「完成品の組」ではなく「ツール単位の小片」にする(ruff、pyright、pytest、uv がそれぞれ check の 1 段、allow の 1〜2 行、CLAUDE.md の 0〜1 行を出す)。合成は連結だけ。2 つ目の言語は需要が出てから |
| F6 | Codex の採否を init 時に固定する設計は「流動的」と合わない | AGENTS.md と CLAUDE.md の切替は機械的(本文を移して `@AGENTS.md` を置く。公式 ◎)。`/import` は Codex の設定を取り込める(公式 ○) | setup の再実行で切り替えられるようにする。注意点を README に: Codex 側には Stop フックが無いので、Codex 利用者のゲートは AGENTS.md の指示と CI だけになる。`CLAUDE.local.md` や `~/.claude/CLAUDE.md` があっても `@AGENTS.md` import 方式なら読まれる(直接読みに頼らない。公式 ◎、issue #103458 ◎) |
| F7 | 更新は「手元の clone がある人」しかできず、プロジェクトが増えると版がばらつく | 上と同じドリフト | lock に版を記録し、doctor.sh が「テンプレートの最新タグとの差」を表示する。install.sh が導入先の一覧をテンプレート clone 側に追記しておけば、一括で版を確認できる(任意) |
| F8 | チーム利用時の衝突点が設計に無い | — | 2.4 に整理 |

## 2. 流動的な適応の仕組みは妥当か

結論: **3 層 + 設定ファイル + 手動の調整スキルという骨格は妥当**で、公開テンプレートの中で更新とカスタマイズを両立している例(spec-kit、OpenSpec、Trail of Bits)と同じ型である。ただし下の 4 点を直さないと、「流動的」が「ばらばらに腐る」になりやすい。

### 2.1 公式機能で置き換えられる部分

自作する前に、次の公式機能を tune / doctor / setup の入力として使う方が保守が軽い。

| 自作しようとしているもの | 公式機能 | 出典 |
|---|---|---|
| 常駐コストの予算点検 | `/context`、`/doctor`(スキル一覧のコスト見積り)、`/skill-doctor`(各スキルのコストと使用回数。`-p` でテキスト出力可) | 公式 ◎ https://code.claude.com/docs/en/skills |
| CLAUDE.md の矛盾・陳腐化の検出 | `/doctor prompt-audit`(v2.1.283+) | 公式 ◎ https://code.claude.com/docs/en/memory |
| 何がトークンを使っているか | `/usage`(10% 以上の要因に推奨を出す) | 公式 ◎ https://code.claude.com/docs/en/costs |
| 摩擦点の抽出(tune の入力) | `/insights`(直近セッションの分析レポート) | 公式 ◎ 同上 |
| 初期セットアップの対話 | `CLAUDE_CODE_NEW_INIT=1` の `/init`、公式プラグイン `claude-code-setup`(自動化を読み取り専用で推薦) | 公式 ○ / 実測 ○ |
| スキルの効果測定 | `claude plugin eval`(あり / なしの差分)、skill-creator | 公式 ○ |

doctor.sh が自前で持つべきなのは、公式が見ないもの(core の改変、lock との不一致、プリセットとスタックのずれ、フック配線の有無、Python の版)だけでよい。

### 2.2 代替案: core を「skills-directory plugin」にする(未検証)

公式には、リポジトリ内の `.claude/skills/<name>/.claude-plugin/plugin.json` をプラグインとしてその場でロードする仕組みがある(公式 ◎ https://code.claude.com/docs/en/plugins/loading)。core をこの形にすると:

- 利点: フックを core ディレクトリ内の `hooks/hooks.json` に置ける。フックは全ソースからマージされて発火するので(公式 ◎)、settings.json に触らずに済み、F2 の問題が消える。update.sh は 1 ディレクトリの入れ替えになり、所有権の境界が物理的に明確になる。
- 欠点(公式の記述): サブディレクトリから起動するとロードされない。信頼ダイアログの承認後にしかロードされず、`-p` でも信頼扱いにならない。スキル名が `/名前:setup` と長くなる。組織の managed settings で無言でブロックされうる。デスクトップアプリの worktree では main 側からロードされる。
- 判断材料: 「他の人や CI でも使う」前提では、`-p` や未信頼状態でフックが効かない点が settings.json 方式(`-p` では未信頼でも動く。公式 ○)と逆になる。CI のゲートは check.sh なので致命的ではない。

推奨は、まず F2 の修正(settings.json に不変の 2 行、update は触らない)で進め、この代替は小さな試行で挙動を確かめてから再評価すること。実機での確認はしていない。

### 2.3 tune が CLAUDE.md を肥大化させる危険

危険は実在する。上述のルール蓄積の事例研究(実測 ○)に加え、公式も「モデル更新後に見直す。旧モデル向けの指示は負担になる」(公式 ◎ https://code.claude.com/docs/en/large-codebases)、「3〜6 か月ごとに設定を見直す」(公式 ○)としている。

修正案:

1. **追加先の優先順位を決める**(上ほど優先)。
   1. ruff / pyright の設定、またはテスト(決定的、トークン 0)
   2. check.sh の 1 段
   3. permissions の ask / deny
   4. フック(例外ゼロの規則だけ)
   5. verify / design スキルの本文
   6. CLAUDE.md の 1 行(lint で書けず、常に要るものだけ)

   設計案の「2 回以上起きて、差分から検出できるもの」は 1〜2 に入る。CLAUDE.md に行くのは「検出できないが常に要る」ものだけになる。
2. **CLAUDE.md は 1 行足すなら 1 行消す。** 上限は project.toml の行数ではなく、提案の規則にする。
3. **削除の契機を明示する。** lock に導入時の Claude Code の版と既定モデルを記録し、doctor.sh がモデル世代の変化を検出したら「全ルールの再評価」を促す。Anthropic は新世代向けに自身の system prompt を 80% 超削った(公式(内部データ)◎)。
4. **「発火しないルールを削除」に加えて「発火しても結果を変えなかったルール」も候補にする。** observe ログに「ブロック → 修正されたか」を残せば判定できる。
5. **tune の提案は LLM 生成である。** 適用は人の承認後という設計案の規則は維持し、提案文をそのまま CLAUDE.md に貼らない(人が短く書き直す)。LLM 生成のコンテキストファイルは成功率を下げた(実測 ○)。

### 2.4 チーム利用時の衝突

| 衝突点 | 修正案 |
|---|---|
| ゲートのモードはコミットされた project.toml にあり全員共通。個人で一時的に切りたい | local 層に上書きを用意する(`settings.local.json` の `env`、または gitignore した `project.local.toml`)。緩める方向の上書きは doctor が表示する。本当の砦は CI |
| stop_gate のログは各自のマシンにある。tune の提案が人によって食い違う | tune の出力は必ず PR にする。ログは gitignore し、提案の根拠(件数)を PR 本文に書く |
| lock ファイルの同時更新でマージ衝突 | lock は 1 ファイル 1 行・ソート済みにする。update は 1 人が 1 PR で行う |
| 協業者はテンプレートの clone を持たない | 更新できるのは保守者だけ、と README に明記。協業者は clone するだけで動く(setup / tune は core に入っているので使える) |
| 協業者の環境で初回にフックが動かない | 対話セッションは信頼ダイアログの承認までフックを保留する(公式 ○)。README に 1 行 |
| ゲートを緩める PR | 設計案どおり人の承認を必須に。CODEOWNERS で check.sh / .claude/ / CI を指定 |

### 2.5 逆輸入(プロジェクト → テンプレート)

手動 PR という方針は妥当。自動化の根拠は見つからなかった。足すとよい規則は 1 つ: 逆輸入の条件を「2 つ以上のプロジェクトで同じ拡張を書いた時」にする。公式の「2 つ目のリポジトリが同じ設定を必要としたら共通化」(公式 ◎)と、前回提案の「同じ修正を 2 回移植した時点で共通化」に揃う。

### 2.6 setup --redetect

妥当。注意点は 1 つ: 検出結果から CLAUDE.md の文章を再生成しないこと。再検出が提案するのは check の段、allow、project.toml の値だけにし、CLAUDE.md は人が書いた部分を保つ。管理ブロックを使うなら、ブロック HTML コメントのマーカーはコンテキストに入らない(公式 ◎)。

## 3. 変えるべき点トップ 5(重要度順)

1. **Stop ゲートの解除を「1 本の規則 + 人へのエスカレーション」にする。**
   「3 ラウンド」と「2 回で通す」を統合し、解除時は理由の作文ではなく、失敗の記録・ユーザーへの表示・判断の依頼にする。observe→enforce の昇格条件を project.toml に書き、doctor が催促する。整形は黙って直す。(A1、A2、A3、S3)

2. **所有権の境界を引き直す。**
   check.sh はコマンドの列だけにしてロジックを core の stop_gate.py に集める。settings.json はマージせず不変の 2 行にする。core は編集しない層と宣言し、`.new` をやめて「止まって差分を表示」にする。(F1、F2、F3)

3. **L3 を公式の型に合わせる。**
   仕様照合は `/code-review` ではなく、設計書を渡す定型のサブエージェント用プロンプトで行う(style 除外、1 回、再レビューは新しい差分のみ)。L とリスクの判定は stop_gate による事後の決定的な検出を足す。(A7、A8、K5)

4. **Stop ゲートに時間予算を持たせ、pyright の範囲を測って決める。**
   署名スキップを明記し、setup が各段の時間を測って fast の構成を決める。pyright は予算内なら全体にかける。失敗時は落ちた段だけを返す。(S1、S2、A4、K3)

5. **tune と不正検知を「足す仕組み」から「正しい場所に置く仕組み」にする。**
   追加先の優先順位、1 行足すなら 1 行消す、モデル世代の変化で再評価、公式の診断コマンドを入力に使う。検査ファイルの保護は事後の警告ではなく permissions の ask に移し、テスト弱体化の検知は人向けの表示にして assert 数は外す。(K4、2.3、A5、A6)

小さいが導入前に直すべきもの: `tomllib` と Python 3.11(F4)、verify スキルを生成後に 1 回実行して確かめる(A9)、CLAUDE.md から verify / design を 1 行ずつ参照する(K1)。

## 4. 小さな 2 点

### 4.1 リポジトリ名「casual-template」

使えるが、変えることを勧める。理由は 3 つ。

- **「template」が実態と合わない。** この設計は core を更新し続けるキットで、コピーして終わりの雛形ではない。GitHub の「テンプレートリポジトリ」機能(更新経路が無い)とも紛らわしい。
- **名前はそのまま名前空間になる。** 設定ファイル名、ログ名、将来プラグイン化した場合のスキル接頭辞(`/名前:setup`)に使われるので、短く、打ちやすい方がよい。
- **「casual」は使い方の気分で、中身を表さない。** 実務にも使う前提と少しずれる。

満たすとよい条件: `claude-` で始めない(プラグイン化した時に `claude plugin validate` がエラーにする。前回提案 §4、公式)、「template」を含めない、10 文字前後、研究版と並べて区別がつく。
候補の例: `devkit`(前回提案の仮名)、`pykit`(Python 中心を明示。ただし将来の他言語と合わなくなる)、`litekit`(研究版との対比)。どれか 1 つを選ぶなら、他言語への拡張余地を残す `devkit` 系が無難。既存の同名プロジェクトとの衝突は未確認なので、決める前に GitHub で検索を。

### 4.2 この設計を docs/design.md として残すべきか

残すべき。ただし形を絞る。

- **残す理由**: この設計は「現行モデルにできないこと」の仮定の束で、Anthropic 自身が半年単位で前提を変えている(既定 effort、plan mode の位置づけ、サブエージェントの用途。サーベイ 4.4)。なぜその部品があるかが書かれていないと、不要になった時に消せない。設計案自身が「戻しにくい判断は ADR」と定めているので、テンプレート自身にも適用するのが一貫している。
- **形**: 決定ごとに「決めたこと / 根拠(URL と取得日)/ 見直す条件」の 3 点を短く。全体で 150 行程度まで。サーベイとこのレビューは、日付入りの資料として別ディレクトリ(例: `docs/research/2026-11-18-*.md`)に置き、design.md からリンクする。
- **注意**: design.md を CLAUDE.md から import しない(常駐コストになる。公式 ◎)。見直す条件には少なくとも「主要モデルの世代交代」「3〜6 か月経過」「observe ログで誤検知が続いた」を入れる。

## 5. このレビューの限界

- 実機での確認はしていない。特に 2.2 の skills-directory plugin の挙動、A10 の「質問ターンでの誤ブロック」の頻度、S2 の時間予算の妥当な値は、導入前の試行で確かめる必要がある。
- 根拠のうち ○ と △ は要約型の取得ツール経由または孫引きで、数値の細部は原典で未照合のものがある。監視の告知が不正を増やすという結果(A5)は研究用モデルのもので、現行の製品モデルに当てはまるかは未確認。
- 組み込みの `/verify` と project 層の verify スキルが同名になる場合の優先関係は確認していない。前回提案は「組み込みはまずプロジェクト側のスキルを探す」としているが、導入前に確かめるか、別名にするのが安全。
- フックのレイテンシ、plan mode のコスト、並列数の根拠は、公式にも第三者にも数値が無い(サーベイ 4.1)。S2 の「15 秒」「10 秒」は例示で、根拠のある値ではない。
