# カジュアル開発用 Claude Code テンプレート 設計提案

作成日: 2026-11-18 / 対象: 設計案のみ(実装・push なし)
調査環境: Claude Code 2.1.326, gh 2.97.0, WSL2。研究版は `claude-ml-template` main(2026-10-01 push)を shallow clone して実測。

凡例: **[実測]** 自分で数えた/計測した。**[公式]** code.claude.com/docs を 2026-11-18 に取得して確認。**[推定]** 根拠はあるが未計測。**[未確認]** 裏が取れていない。

---

## 1. 結論(一画面要約)

1. **自作エージェントは 0 個で始める。** 役割分離は組み込み機能で賄う: 計画 = plan mode、独立レビュー = 同梱の `/code-review`(会話を見ていない別コンテキストで走る)、探索 = 組み込み Explore。ルーターは置かず、規模判定は CLAUDE.md の数行でメインに判断させる。
2. **機械ゲートは 2 本だけ。** Bash の危険操作ガード(PreToolUse)と、Stop 時の `check.sh`(整形→lint→型→速いテスト)。どちらも off / observe / enforce の 3 モードで、observe から入る。
3. **常駐コンテキストは CLAUDE.md 約 30 行 + スキル説明 1 個。** 研究版の常駐分 約 6,400 字 → 約 900 字(約 85% 減)[実測+推定]。ただし後述のとおり、研究版のコストの主因は常駐分ではないので、効くのは 4 のほう。
4. **トークンと時間の本丸は「起動ごとのコスト」を消すこと。** 研究版は `/ml-pipeline` 本文 22,018 字が呼ぶたびに会話へ入り、L 経路で最低 6 回サブエージェントをコールドスタートし、Edit 1 回ごとに `uv run python` を 6 プロセス起動する [実測]。カジュアル版はこれを全部なくす。
5. **配布はプラグイン 1 個(自分のマーケットプレイス、タグ/SHA 固定)+ `init` スキル。** フックと手動スキルはプラグインで全プロジェクト共通に配り、プロジェクト固有の小さなファイル(CLAUDE.md、permissions、check.sh、verify スキル)だけ init がその場で生成してコミットする。curl|bash はやめる。
6. **研究版とは独立リポジトリ。** コード共有はしない。将来、研究版を「カジュアル core + 研究プラグイン」に寄せられるよう名前だけ揃えておく。
7. **足す前に測る。** フェーズ 0 で素の Claude Code を対照として 3 タスク計測し、以後スキル/ルールの追加は「あり/なし」比較を通ったものだけにする(研究版 `ideas/harness-upgrade-summary.md` の運用ルールを継承)。

たたき台からの主な変更: エージェント最大 3 個 → 0 個 / コンパクト前チェックポイントのフック → 廃止(組み込みで足りる)/ 編集ごとの自動整形 → Stop 時に 1 回 / brainstorm・adr・コミット補助スキル → 標準から外す / curl|bash → プラグイン。

### 2.1 トークン削減

| 施策 | 根拠 |
|---|---|
| 自作エージェント 0、ルーターなし | サブエージェントは親のキャッシュを読めず、独自のシステムプロンプトで一から温める。TTL もサブスクでも 5 分 [公式: prompt-caching「Subagents and the cache」]。カスタムエージェントは CLAUDE.md と git status も読み込む [公式: sub-agents]。「同じモデルが同じ課題をやるので、並列性か新しい目は得られるが賢い答えにはならない」[公式: best-practices「Know what subagents cost」] |
| 手動専用スキルは `disable-model-invocation: true` | この指定で説明文がコンテキストに載らない = 常駐 0 [公式: skills の表] |
| スキルに `model:` を書かない | インラインスキルの `model:` はそのターンがモデル切替になり、会話全体がキャッシュミスする [公式: prompt-caching「Switching models」]。安いモデルを使いたい処理は `context: fork` 側で指定する |
| ルールは CLAUDE.md に畳むか `paths:` 付きにする | paths なしルールは CLAUDE.md と同じく常駐、paths 付きは該当ファイルを触った時だけ読まれる。`@import` は常駐コストを減らさない [公式: memory] |
| CLAUDE.md は約 30 行、人間向けメモは HTML コメントに | 200 行未満推奨、ブロック HTML コメントは注入前に除去される [公式: memory] |
| フック出力を絞る | Stop フックの stderr はそのまま Claude に返る。gate は末尾 40 行だけ返す。上限は 10,000 字で超過分はファイル退避 [公式: hooks]。公式もテスト出力を tail する前処理フックを例示 [公式: costs] |
| 整形は編集ごとではなく Stop 時に 1 回 | 編集後に外部でファイルが変わると変更通知が会話に足される [公式: prompt-caching「file-change notices」に言及あり]。通知 1 件あたりのサイズは [未確認]。フェーズ 0 で比較する |
| セッション途中でモデル/effort を変えない運用を README に明記 | モデルごとにキャッシュが別 [公式]。`opusplan` は plan mode の出入りごとに切替になる [公式] |
| GitHub 操作は MCP でなく `gh` | CLI はツール一覧を足さない [公式: costs] |

捨てる研究版要素: `/ml-pipeline` コマンドと references、エージェント 19 個、scout 6 種、output-style、agent teams 有効化(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`。plan mode のチームは標準の約 7 倍 [公式: costs])、AGENTS.md 生成。

トレードオフ: 常駐の削減は絶対値で数千トークン/リクエスト、しかもキャッシュ読み単価なので金額効果は小さい。効くのはパイプライン本文とサブエージェント起動の廃止だが、その実額は未計測(§9)。

### 2.2 正確さ

| 施策 | 根拠 |
|---|---|
| Stop 時に決定的チェック(`check.sh`)を強制 | 「必ず起きてほしいことはフックに。CLAUDE.md は指針で、Claude は適用しない判断ができる」[公式: best-practices]。資料 1 も検証ループを基本部品としている |
| プロジェクト固有の `verify` スキル(起動方法と見るべき点)を init 時に Claude に書かせる | テストと型で漏れる不具合を実動作で拾う [公式: best-practices の `/verify`]、資料 1「verify を関連コードの近くに」。組み込みの run/verify はまずプロジェクト側のスキルを探す |
| 独立レビューは `/code-review` を 1 人だけ、L またはリスク該当時に「提案」 | 会話を見ていない別コンテキストで diff を見る [公式: code-review-local]。レビュアーを積むより 1 人を調整(資料 1)。研究版サーベイ R7「レビューボットの signal ratio は平均 60% 未満、増やすだけではノイズ」(`literature/.../summary.md` §4。元論文は [未確認])。公式も「レビュアーは必ず何か見つける。全部直すと余計な抽象が増える」 |
| リスク条件(認証・秘密情報・依存追加・削除/移行・公開 IF)を規模と別軸で持つ | 研究版サーベイ I5(リスク階層)と router.md の「迷ったら中」の知見。CLAUDE.md に 1 行 |
| バグ修正は「失敗するテストを先に」 | 研究版サーベイ V3/V10(LLM は現行実装を写したアサーションを書きがち)。CLAUDE.md に 1 行。tdd_gate のような機械強制はしない |
| 同じチェックが 3 回落ちたら止まって報告 / 破壊的操作は実行前に案を見せる | 資料 1 / 資料 2。CLAUDE.md に各 1 行 |
| ゲート自体を変更から守る | gate.py と guard.py はプラグインキャッシュ側にあり、プロジェクトの diff では書き換わらない(資料 1「変更が自分のチェックを書き換えられない」の簡易版)。`check.sh` と `.claude/settings.json` の編集は permissions の ask に入れる |
| 見逃しはルール化、月 1 で刈る | 資料 1(2 回以上起きたものだけ昇格)。刈り込みは `/doctor prompt-audit` と `/skill-doctor` [公式] |

捨てる研究版要素: evaluator 2 軸、plan-premortem、refuter、counterexample-hunter、spec-auditor、final-gate、cross-review(Codex)、spec_gate / plan_gate / tdd_gate / requirements_gate / state_gate、データ保護一式、ML スキル。

トレードオフ: 実装者と採点者の分離を常時強制しなくなる。自己採点バイアスは決定的チェックと任意の `/code-review` で受ける設計で、L を黙って通した場合の見逃しは研究版より増えうる。なお `REVIEW.md` はローカルの `/code-review` では読まれない(GitHub 上のマネージド Code Review 用)[公式]。ローカルで観点を足すなら CLAUDE.md に書くか、REVIEW.md を読む自前の fork スキルを後から足す(フェーズ 3)。

### 2.3 高速開発

| 施策 | 根拠 |
|---|---|
| 既定経路は「何も挟まない」。S/M は計画も審査もなし、L だけ plan mode | 研究版 README §0 も単発作業は直接実行を勧めている。plan mode の指示は会話末尾に足されるだけでキャッシュを壊さない [公式] |
| フックは `python3` 直呼び・標準ライブラリのみ | `uv run python` 0.33 秒に対し 0.009 秒 [実測]。この環境に jq は入っていなかったので jq 依存の sh は不可 [実測] |
| Edit 時のフック 0 本、Bash 時 1 本、Stop 時 1 本 | 研究版は 6 / 2 / 8 本 [実測] |
| gate は「前回 PASS 時から作業ツリーが変わっていなければ即終了」 | 研究版 quality_gate.py の署名スキップを継承。質問だけのターンを遅くしない |
| gate は 60 秒で打ち切り、同一セッション 2 回ブロックしたら次は通す | 資料 1。ハーネス側にも連続 8 回の上限と `stop_hook_active` がある [公式: hooks] |
| `spike/*` `proto/*` ブランチでは gate を自動で off | プロトタイプ用。スキルを足さずブランチ名で切る(常駐 0) |
| permissions の allow をプリセットで埋める | 新規セッションは auto mode で始まる [公式: best-practices] ので承認待ちは既に少ない。deny/ask は auto mode より前に効く [公式] |
| フラグは 1 個(gate のモード)だけ | 研究版の約 30 フラグは設定と検証の負担 |

捨てる研究版要素: design-interview 必須化、spec-checklist、承認ゲート、セッション監視/再開/レポート生成フック、notify。

トレードオフ: Stop 時チェックはターン末に数秒〜数十秒足す。flaky なテストがあると 2 回は余計に回る。

## 3. エージェント分離: 「最小」を推奨(自作定義は 0 個)

選択肢の比較:

| 案 | 追加コスト | 正確さへの寄与 | 判定 |
|---|---|---|---|
| ルーター付き(haiku router → 経路分岐) | 依頼ごとにコールドスタート 1 回 + 待ち時間。研究版では経路記述のため 22,018 字のコマンド本文も必要だった [実測] | 規模判定そのものはメインが文脈内でほぼ無料でできる | 不採用 |
| 自作 3 個(explorer / planner / reviewer) | 説明 3 個の常駐は小さい。起動ごとにコールドスタート、CLAUDE.md 再読込、既読ファイルの再読 | planner と reviewer は組み込み(plan mode, `/code-review`)と重複し、保守だけ増える | 不採用 |
| **最小(自作 0、組み込みを使う)** | 0 | 独立レビューだけが分離の利得。それは `/code-review` で得られる | **採用** |
| 分離なし(レビューも同一コンテキスト) | 0 | 自己採点バイアスが残る | 不採用 |

理由:

- 分離が正確さに効くと公式・資料 1・研究版サーベイが一致して言うのは「書いた経緯を知らないレビュアー」だけ。計画と実装を別コンテキストに分けると、引き継ぎ文に載らなかった情報が落ち、再読コストを払う(公式: 「fresh subagent は文脈を集め直すので遅くなりうる」)。
- `/code-review` は同梱で SKILL.md を持たず、バックグラウンドの別コンテキストで走り、CLAUDE.md に従い、effort で広さを変えられる [公式]。自作 reviewer はこれの劣化コピーになる。
- reviewer の自動起動はしない。L またはリスク条件に当たったとき、完了報告の中で「`/code-review low` を勧める」と 1 行出させるだけにする。毎回自動だとトークンとノイズ(R7)の両方が増える。

後から足す条件(計測してから):

- `/usage` の内訳でサブエージェント/探索の比率が 10% を超えたら、`model: haiku` + `omitClaudeMd` の explorer を 1 個足す。公式ドキュメントの現行記述では組み込み Explore は親と同じモデルで動き、安くしたければ haiku の定義を自分で置く、とある(要再確認。§9)。
- L タスクで「テストは通るが仕様違い」が 2 回起きたら、`SPEC.md` と diff を突き合わせる fork スキルを 1 個足す。

未計測: サブエージェント 1 回のコールドスタートが実際に何トークンか。フェーズ 0 で、同じ M タスクを「直接」「`/code-review` 付き」で流して `/usage` を比べる。

## 4. ファイル構成案

配布リポジトリ(名前は仮。`claude-` で始まるプラグイン名は `claude plugin validate` がエラーにする [公式: manifest-reference] ので避ける。研究版の `claude-ml-template` はこれに当たる):

```
devkit/
├─ .claude-plugin/marketplace.json      プラグイン 1 個を相対パスで載せる
└─ plugins/devkit/
   ├─ .claude-plugin/plugin.json        name, description。version の扱いは §5
   ├─ hooks/hooks.json                  PreToolUse(Bash)→guard.py / Stop→gate.py の 2 本
   ├─ scripts/guard.py                  約 80 行。python3 標準ライブラリのみ
   ├─ scripts/gate.py                   約 100 行。check.sh 実行・署名スキップ・tail・モード
   ├─ skills/init/SKILL.md              手動専用。プロジェクト側ファイルを生成
   ├─ skills/handoff/SKILL.md           手動専用。引き継ぎメモを書く
   ├─ skills/fix-ci/SKILL.md            手動専用。!`gh run view --log-failed | tail -100` を注入
   ├─ templates/CLAUDE.md.tmpl
   ├─ templates/presets/python/         check.sh, permissions 断片, rules/python.md
   └─ templates/presets/node/           同上(2 個目は需要が出てから)
```

プロジェクト側(`/devkit:init` が生成し、ユーザーが差分を見てコミット):

```
CLAUDE.md                        約 30 行
.claude/settings.json            permissions(allow/ask/deny)
.claude/devkit.json              {"gate": "observe"}
.claude/check.sh                 整形→lint→型→速いテスト。編集可
.claude/rules/<lang>.md          paths 付き、約 15 行
.claude/skills/verify/SKILL.md   起動方法と確認点。Claude が生成
```

| ファイル | 役割 | 常駐コスト |
|---|---|---|
| CLAUDE.md | コマンド 4 行、構成 3 行、作業ルール 6 行(規模 S/M/L、リスク条件、失敗テスト先行、3 回で停止、破壊的操作は案から、compact 指示) | 約 800 字(概算 0.6〜1.0k トークン [推定]) |
| verify スキルの説明 | モデルが自発的に使う唯一のスキル | 約 100 字 |
| init / handoff / fix-ci | `disable-model-invocation: true` | 0 |
| rules/<lang>.md | 該当拡張子を触った時だけ読まれる | 0(読込時 約 400 字) |
| guard.py | `rm -rf` の対象判定、`git add -A`/`.`、main への force push、コマンド中の秘密らしき文字列、`.env` へのリダイレクト。ブロック時のみ 1 行返す | 0 |
| gate.py | モード判定 → 変更なしなら即終了 → `check.sh` を 60 秒上限で実行 → 失敗時のみ末尾 40 行を返す。observe ではログのみ | 通過時 0 |
| settings.json | deny: `Read(./.env*)`, `Edit(./.env*)`, `Bash(sudo *)` など / ask: `git push`, 依存追加, `Edit(.claude/check.sh)`, `Edit(.claude/settings.json)` / allow: プリセットのテスト・lint | 0 |

常駐合計 約 900 字(研究版 約 6,400 字)。プリセットは別プラグインにしない。ルールと permissions はプラグインで配れないため(§5)、プリセットは init が使うテンプレートの束で足りる。

たたき台との差分: 「コンパクト前チェックポイント」フックは置かない。圧縮後も CLAUDE.md は再読込され、呼んだスキルは再添付され、`/resume` とセッション要約がある [公式: skills, prompt-caching]。必要なら CLAUDE.md の「Compact instructions」1 行で足りる。研究版はここに 4 フック約 26 KB を使っている [実測]。

## 5. 配布・更新方式

| 方式 | 配れるもの | バージョン固定 | 失敗時 | 供給網リスク | 評価 |
|---|---|---|---|---|---|
| curl \| bash(研究版の現行) | 何でも | なし(常に main) | `.claude/` を上書き、ロールバックなし | 未固定のリモートスクリプトを実行 | 不採用 |
| タグ固定の clone + ローカルスクリプト | 何でも | タグ | 上書き型は同じ | 中身を読んでから実行できる | 予備 |
| **プラグイン + 自前マーケットプレイス** | スキル、エージェント、フック、MCP、bin。**CLAUDE.md は不可**(明記)。rules と permissions は manifest にフィールドがない [公式: manifest-reference] | マーケットプレイスの `ref` をタグ/SHA に、プラグイン `sha` も可 [公式: marketplace-reference] | 旧バージョンのディレクトリは 14 日残る。更新は次回起動で反映 [公式: loading] | サードパーティは自動更新が既定 off [公式] | **採用** |
| `gh skill`(preview) | スキルのみ | `--pin` でタグ/SHA [実測: `gh skill install --help`] | staging 入替は資料 3 の自作運用 | preview で仕様変更あり [公式: cli.github.com] | フック・設定を配れないので主軸にしない |
| git subtree / submodule | 何でも | コミット | `.claude/` にプロジェクト固有物が混ざり衝突する | 低 | 個人用途には重い |
| GitHub テンプレートリポジトリ | 何でも | なし | 更新経路がない | 低 | 不採用 |

推奨の運用:

- 導入は 1 回: `claude plugin marketplace add <owner>/devkit@v0.1.0` → `claude plugin install devkit@<marketplace> --scope user`。以後どのプロジェクトでもフックと手動スキルが効く。プロジェクトごとの作業は `/devkit:init` だけ。
- プラグイン側フックは `"$CLAUDE_PROJECT_DIR/.claude/check.sh"` が無ければ何もしない。init していないプロジェクトには影響しない。
- 更新: タグを切り、`ref` を上げて `claude plugin update`。`plugin.json` に `version` を書くと、その文字列を変えるまで利用者は更新を受け取らない [公式: loading]。研究版の plugin.json は `"version": "1.0.0"` 固定なので、プラグインとして使うとこの罠に当たる。カジュアル版は `version` を書かずコミット SHA 追従にし、固定はマーケットプレイスの `ref` で行う。
- 供給網: 自分のリポジトリのみ、タグ/SHA 固定、導入時にサードパーティの npx を実行しない(資料 2)。ドメイン特化エージェントは同梱せず、必要時に個別に入れる。

弱点: スキル名が `/devkit:handoff` のように長くなる。`skillOverrides` はプラグインスキルに効かない [公式]。クラウドセッションはリポジトリの `extraKnownMarketplaces` を追加しない [公式: loading]。協業者や CI でも同じゲートを効かせたいなら、フック 2 本をリポジトリ内にコピーする方式に切り替える必要がある(§8 質問 3)。

## 6. 研究版との関係: 独立(コード共有なし)

- 研究版のフックは `_common.py`(15 KB)・`uv run`・フラグ群・データ保護に結合しており、切り出すと複雑さごと持ち込む。`invariants.md` は guard の緩和を禁じているので、カジュアル向けの緩いガードと同じコードにできない。
- 引き継ぐのはコードでなく知見: 誤検知はエージェントが回避策を探すトークン浪費になる(guard_bash のコメント)、`git add` の一括ステージ禁止、署名による再実行スキップ、ツール欠落判定は stderr だけで行う、リスク階層は「迷ったら中」。
- 将来像: 研究版 ideas ④ の「light プロファイル」がこのカジュアル版に当たる。研究版を「devkit core + 研究用プラグイン」に組み替えられるよう、同じマーケットプレイスに並べられる命名にしておく。共通化に着手するのは、同じ修正を両方に 2 回移植した時点。

## 8. 未決事項とユーザーへの質問(優先度順)

1. **主に使うスタックは何か。** 最初のプリセットを 1 個に絞るため(Python/uv、TypeScript/Node、ほか)。
2. **対象 OS は WSL/Linux(+ macOS)だけでよいか。** よければフックは `python3` 直呼びで確定。Windows ネイティブも要るなら PowerShell 版の二重保守になる(研究版は .sh と .ps1 を全部二重に持っている)。
3. **自分 1 人の端末だけで使うか、協業者・CI・クラウドセッションでも同じゲートを効かせたいか。** 前者ならユーザースコープのプラグイン、後者ならフックをリポジトリ内に置く。
4. **課金形態(サブスクか API か)と普段のメインモデル。** サブスクならキャッシュ TTL が 1 時間で常駐コストはさらに軽く、待ち時間のほうが重要になる。API なら haiku explorer の優先度が上がる。
5. **独立レビューを自動で走らせたいか。** 推奨は「自動では走らせず、L またはリスク条件のときに提案だけ」。L で毎回自動にしたい場合はトークン増を承知で Stop 側に組み込む。

## 9. リスクと、この提案が間違っていそうな箇所

- **トークン数は文字数からの概算で、実トークナイズも `/usage` 計測もしていない。** 日本語は 1 字あたりのトークンが英語より多く、CLAUDE.md を英語で書けば減る可能性があるが未計測。サブエージェント 1 回のコールドスタート量、ファイル変更通知のサイズも未計測。フェーズ 0 で覆る余地がある。
- **「自作エージェント 0」は L タスクで甘い可能性が最も高い。** 複数ファイルの機能追加で仕様違いが通るようなら、L での `/code-review` 自動化か SPEC 突き合わせスキルが必要になる。資料 1 の「別グレーダーで最大 10 ポイント向上」は自己申告だが、方向は逆を指している。
- **組み込み機能への依存。** plan mode、`/code-review`、`/verify`、auto mode 既定、Explore のモデル、プラグインの制約は 2026-11-18 時点のドキュメント記述で、一部ページは長く要約モデル経由で読んだ。特に「Explore は親モデルで動く」は実装前に再確認が要る。仕様が変わればテンプレート側に穴が開く。
- **規模判定を CLAUDE.md の文章に任せる点は決定的でない。** 過小判定(本当は L なのに直接実装)を止める仕組みがない。研究版 router の「迷ったら L」を捨てている。
- **Stop 時チェックの体感。** 変更のあるターンは毎回走る。テストが遅いプロジェクトでは `check.sh` を lint と型だけに削る判断が要り、そうすると正確さの柱が細る。
- **プラグイン配布の前提。** クラウド/リモートセッションを多用するなら不適。ユーザースコープのフックは全プロジェクトで起動する(check.sh が無ければ即終了するが、python3 起動 約 10 ms は毎回かかる)。
- **Stop 時整形。** 編集ごとの整形をやめる根拠(変更通知のトークン)は未確認で、逆に Stop 時に整形差分が出てコミット前の差分が読みにくくなる可能性がある。
- **研究版メモ内の arXiv 番号・数値(SkillsBench、R7 の 60% など)は自分では原典を確認していない。** 方向性の補強に使っただけで、数値は引用しないほうがよい。
- **資料 1 の数値はすべて社内自己申告。** 採用したのは仕組み(3 回で停止、3 モード、2 回ブロックで通す、レビュアー 1 人)で、数値には依存していない。
