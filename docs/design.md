# devaccel 設計記録

作成 2026-11-18。各決定は「決めたこと / 根拠 / 見直す条件」。根拠の詳細と出典 URL は `docs/research/` にある。

- `2026-11-18-survey-4axes.md`: トークン・正確さ・速度・多プロジェクトのサーベイ(公式資料優先)
- `2026-11-18-proposal.md`: 初回提案(研究版の実測を含む)
- `2026-11-18-design-review.md`: 設計案のレビュー(本設計に反映済み)

**全体の見直し条件**: 主要モデルの世代交代 / 3〜6 か月経過 / observe ログで誤検知が続く。

## 目標

個人開発 + 軽い実務。Python 中心、WSL/Linux。他の人と CI でも同じ担保が効くこと。評価軸: (1) トークン削減 (2) 正確さ (3) 高速開発 (4) 多様なプロジェクトへの対応と流動的な変化。

## D1. 最小構成から始め、必要になってから足す

- **決定**: 常駐は CLAUDE.md(約30行)+ スキル説明 2 件(design, verify-app)。rules ファイル、自作エージェント、ルーターは置かない。
- **根拠**: 公式は「設定なしで大半は動く、拡張は必要になってから」。Anthropic 自身のリポジトリは CLAUDE.md 40 行で agents/hooks なし。長いコンテキストファイルはコスト増で成功率を上げない(実測)。研究版の負担は常駐(約 6,400 字)より起動ごとのコスト(22,018 字のコマンド本文、L で 6 回以上のサブエージェント)だった。
- **見直す条件**: `/usage` で探索の比率が 10% 超 → haiku の explorer を 1 個検討。

## D2. 自作エージェント 0。独立レビューは L のみ、仕様照合に限定

- **決定**: L 規模の実装後に、design スキルが定型プロンプトでサブエージェントを 1 体起動し、設計書の受け入れ条件との照合だけをさせる(スタイル除外、再レビューは新差分のみ、3 ラウンドまで)。
- **根拠**: サブエージェントは親のキャッシュを読めずコールドスタート。評価役つき構成は単独の約 20 倍のコスト(公式: 単独で確実にできない作業でだけ元が取れる)。レビュアーは必ず何か見つけるので仕様照合に絞る(公式)。組み込み `/code-review` は観点を外から絞れず REVIEW.md も読まない。
- **見直す条件**: L で仕様違いが 2 回すり抜けたら、照合専用エージェント定義(Read/Grep/Glob のみ)を追加。最も外れやすい判断(資料の「別グレーダーで最大 10pt 向上」は逆方向を示す)。

## D3. 正確さは機械ゲートと実動作確認で担保する

- **決定**: L1 Stop ゲート(`check.sh fast`)/ L2 verify-app(実際に動かす)/ L3 仕様照合(L のみ)/ L4 CI(`check.sh full`)。
- **根拠**: 検証ループが委任の基本部品、E2E がテストより重要、安いチェックを先に(Claude Code チーム)。生成テストを通るパッチの 22〜33% が隠しテストで落ちる(実測)ため、テスト通過だけを完了条件にしない。
- **見直す条件**: verify-app が使われない(スキル未起動率が高い)なら CLAUDE.md の参照行を強める。

## D4. Stop ゲートの挙動

- **決定**: 解除規則は 1 本: 失敗段の修正が `max_rounds`(3)回続いたら、Claude に修正停止とユーザーへの報告を指示し、ユーザーにも `systemMessage` で表示。理由の作文で通す仕組みは作らない。observe → enforce は `promote` 条件を満たしてから。前回から作業ツリーが変わっていないターン、docs のみ、`spike/*` では走らない。整形は fast 内で自動修正。失敗時は落ちた段の出力だけ返す。L 相当の規模・リスクパス・テスト削除・skip 追加は **人向けの表示のみ**(ブロックしない、セッションで種類ごとに 1 回)。
- **根拠**: 人へのエスカレーションはテスト不正を減らした(実測、要原典確認)。自己申告の理由は検証されない。公式もフックの誤発火を認める → observe から。汎用の出力圧縮は効かず、エラーを隠すとループが増えた(実測)。
- **見直す条件**: observe ログで質問ターンの誤ブロック相当が目立つ → テスト段の発火条件を絞る。

## D5. フックは 2 本、python3 標準ライブラリ

- **決定**: guard(PreToolUse Bash)と stop_gate(Stop)のみ。`uv run` を使わず `python3` を直接呼ぶ。宣言で書ける規則(.env 読み取り、検査ファイルの編集)は permissions の deny/ask に置く。
- **根拠**: 公式「フックは例外ゼロの規則だけに」。起動時間の実測は `uv run python` 0.33 秒、`python3` 0.009 秒。ask/deny はプロセスを起動せず auto mode より先に効く。
- **見直す条件**: Windows ネイティブ対応が必要になったら node(exec 形式)を検討。

## D5b. 秘密はサンドボックス、guard は破壊的操作だけ(0.2.0)

- **決定**: guard から `.env` 検出を削除。秘密はサンドボックスの `denyRead`(シェル)と permissions の deny(Read ツール)で守る。guard は heredoc を含む生のコマンド文字列に規則を当てる(パーサ差異を作らない)。
- **根拠**: 0.1.1〜0.1.12 で自動セキュリティレビューと誤検知修正が交互に続いた(誤検知を直すと抜け道、抜け道を塞ぐと誤検知)。L 規模の実地テストでは誤検知で Bash が 2 回止まり、`-p`・並列実行では確認=拒否になるため速度に直結。公式も強い保護は OS レベルのサンドボックス。
- **見直す条件**: サンドボックスが使えない環境(ネイティブ Windows 等)を対象に加える時。

## D6. 検査を書き換えさせない

- **決定**: `scripts/check.sh`・`.claude/hooks/**`・settings.json・project.json・CI の編集は permissions の `ask`。テスト弱体化は人向けに表示。チームでは CODEOWNERS + ブランチ保護。assert 数の検知はしない(誤検知が多い)。
- **根拠**: 「変更は自分のチェックを変えられない」(Claude Code チーム)。リポジトリ内コミット方式ではプラグインキャッシュの保護が無い。

## D7. 設計は規模に比例させる

- **決定**: S なし / M 3 行方針 / L は plan mode + design スキル(選択肢つき質問を 1 往復、受け入れ条件に確認方法を付けた設計書を plan と兼用、承認後 docs/design/ に保存)。戻しにくい判断は ADR。
- **根拠**: 仕様先行は小さな変更・バグ修正では差がなく時間とトークンだけ増える(実測)。計画段階での人の承認は効果が大きい(公式、内部データ)。
- **見直す条件**: S/M の過小判定で事故 → `scale` の閾値か risky_paths を調整。

## D8. 配布: タグ固定の clone + install.sh、リポジトリ内にコミット

- **決定**: curl|bash もプラグインも使わない。導入先には `.claude/` ごとコミットし、他の人は clone するだけ。
- **根拠**: プラグインは CLAUDE.md・rules・permissions を運べず、更新も既定で伝播しない(公式)。自動更新は任意コード実行と同じ(公式)。`gh skill` は preview でスキルしか配れない。
- **見直す条件**: skills-directory plugin(リポジトリ内でその場ロード)を小さく試し、フック配線と `-p`/未信頼時の挙動が許容できれば core をそちらへ。

## D9. 3 層の所有権と更新

- **決定**: core(キット所有・編集しない)/ project(生成後は自由)/ local(個人・gitignore)。update は lock のハッシュで core の手編集を検出したら止まって差分を表示(`.new` は置かない)。staging してから置換。settings.json はマージしない(install 時に 1 回、doctor が配線を点検)。check.sh はコマンドの列だけにし、ロジックは core の stop_gate に集める。
- **根拠**: コピー方式のドリフトと、settings の機械マージの壊れやすさ(実測・issue)。spec-kit / OpenSpec と同じ型。`gh skill update` はローカル追加を消す(実測)。
- **見直す条件**: 手編集で止まる頻度が高い → 該当の調整点を project.json に追加する。

## D10. 流動的な適応

- **決定**: 調整点は `project.json` に集約(JSON: Python 3.10 でも標準で読める)。プリセットはツール単位の小片(ruff/pyright/pytest)の連結。`/devaccel-setup --redetect` は check の段・allow・project.json だけ提案し、人の書いた文章は再生成しない。`/devaccel-tune` は「2 回以上・機械的に検出可能」なものだけ追加し、追加先は lint/テスト → check.sh → permissions → フック → スキル → CLAUDE.md の順。CLAUDE.md は 1 行足すなら 1 行消す。ゲートを緩める提案は人の明示承認が必須、チームでは PR。2 つ以上のプロジェクトで同じ拡張をしたらキットへ逆輸入。
- **根拠**: ルール文は放置すると増え(1 リポジトリで 4.9k→17.4k 語)、旧ルールの多くは新モデルで不要だった(実測)。公式は「モデル更新後に見直す」。公式の診断(`/context`、`/usage`、`/insights`、`/doctor`)を tune の入力に使う(実在はバージョン依存、要確認)。
- **見直す条件**: 2 つ目の言語のプリセットが必要になった時点で小片を追加。

## D11. 並列開発: 並列化は公式、devaccel は「証拠」と「振り分け」

- **決定**: 作業の分割と並列実行は公式 `/batch`(worktree ごとに実装して PR まで)に任せ、自前のオーケストレーターは作らない。devaccel は PR 本文を機械的に組み立てる証拠(check.sh full・実動作確認・受け入れ条件・規模)と、`evidence-ok` / `needs-human` の振り分けを担う。自動マージは evidence-ok のみ・既定 off。並列度は `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=3`。L は並列化しない。
- **根拠**: Claude Code チームは「検証ループがあるから数十〜数百を並列に動かせる」「失敗したチェックが人の見る場所を決める」「未検証も記録する」。公式: 並列はトークンを並列数倍に増やす。本文を LLM に書かせると自己申告になるため、スクリプトで組み立てる。
- **見直す条件**: evidence-ok からリバートや不具合が出たら、それを検出できる段を足す(tune)。needs-human ばかりなら閾値を見直す。

## D12. 並列 PR の統合: ローカル・マージキュー(0.5.0)

- **決定**: 人が実行する `devaccel_land.py` を足す。`evidence-ok` の PR を番号順(docs のみの PR は最後)に最新 base の一時 worktree へ `merge --no-ff` し、そのつど base の `check.sh full`。衝突・失敗は `needs-human` に降格(昇格しない)。`--merge` で通過分を `gh pr merge --squash --match-head-commit`、マージ前に base が動いていないこと、マージ後の木が検証した木と一致することを確認。Claude からの `--merge` は guard が拒否。PR 本文に `devaccel:evidence base=… head=…` を記録し、PR スクリプトの再実行は既存 PR を更新する。ドキュメントの追随は単位の切り方(docs は振る舞いを変えた単位が更新)で対処し、docs 未変更は表示のみ。
- **根拠**: 試行で /batch の 3 PR を順にマージした際、各 PR の証拠は兄弟のマージ後には古かった(今回は運よく衝突なし)。README 単位が他単位の新オプションを書けなかった。GitHub の「最新必須」やマージキューはプランにより非公開リポジトリで使えない。rebase + force push は guard の緩和と検証済み SHA の変化を招く。Claude にマージさせると自分の PR を自分で通す構図になる。統合は機械的で LLM トークン 0。
- **受け入れたリスク(0.5.3 で打ち止め)**: 「マージは人だけ」を guard の文字列判定と land の端末確認で完全には守れない。疑似端末・展開・別名の抜け道は無限にあり、さらにサンドボックス内からも gh の認証情報と api.github.com に届くため、land を経由しなくても API で直接マージできる。正規表現の追加はここで止め、本当の境界は GitHub 側とする(0.5.4 で `protect.sh`)。Claude も同じアカウントのトークンで動くので「承認必須」は個人では使えない(自分の PR を承認できない)。保護は「直接・force push 禁止(管理者も)、PR 必須、CI `check` 必須(strict なし: land が統合を検証するため)」。残るリスクは「緑の needs-human PR を Claude が API でマージしうる」で、guard の gh 拒否が best-effort で抑える。完全にするには Claude 用に権限の弱い別アカウント/トークンが要る。ユーザーは公開してブランチ保護を使う方針(2026-11-18)。
- **見直す条件**: 直列の full 実行が遅すぎる(PR 数 × full)なら、衝突しない PR をまとめて 1 回検証する。GitHub のマージキューが使える環境ではそちらに寄せる。

## D13. 並列時のトークン: 単位の固定費を削る(0.6.0)

- **事実(公式)**: サブエージェント(/batch の単位)は親のプロンプトキャッシュを共有せず、worktree ごとに作業ディレクトリが違うので単位間でも共有されない。サブエージェントのキャッシュ TTL は 5 分。単位は CLAUDE.md 等を読み直して始まる。
- **決定**: 並列化の閾値を上げる(4 件以上、2〜3 件は逐次でメインの 1 時間キャッシュを使う)、計画役が単位にコンテキストパックを渡して再探索を減らす、読む価値のないパスを deny。単位のモデルを下げる(`CLAUDE_CODE_SUBAGENT_MODEL`)のは計測で品質(needs-human 率)を比べてから。
- **副産物**: 調査で単位内ゲートの不発(SubagentStop 未登録・本体の木を検査)が見つかり修正。試行のゲート記録が 2 回の /batch(6 単位)で計 5 件しかなかったことと整合。
- 出典: code.claude.com/docs/en/prompt-caching, /sub-agents, /hooks, /worktrees, /costs

## D14. 計測にもとづく調整(0.7.x)

- **ベンチ(sonnet、小課題 3 つ、各 1 回)**: vanilla 平均 $0.163 / 12 ターン / 35 秒。devaccel 0.6.x は $0.21 / 17 / 97 秒、0.7.1 は $0.184 / 15 / 45 秒。正確さ(隠しテスト・check full)は全条件で満点。アブレーション(verify 行なし、進め方・検証の節なし)でもコストは $0.18〜0.19 で、残る差は CLAUDE.md の文言ではなくゲート・サンドボックス・読み込み増と推定。n=1 なので大きさは不確か。
- **並列フロー(/batch 3 単位)**: 0.7.1 で 3/3 が evidence-ok の PR に到達($1.13)。そこまでに見つかった実地の障害: 単位内ゲート不発(0.6.0/0.6.4)、worktree Read deny(0.6.4)、展開を含む Bash の拒否(0.6.5/0.7.1)、`.claude/` 配下の Write の保護(0.7.1)。land は重なる 2 本を衝突として正しく降格。
- **難課題(haiku、罠つき 3 課題 × 2 回、0.7.2)**: vanilla・devaccel とも隠しテスト全通過(h1 9/9、h2 10/10、h3 41/41)、check full も全通過。devaccel は時間が約 2 倍(h1 45→135 秒、h2 86→165 秒)、コストはほぼ同じ。今のモデルは単一セッションの罠を検証の仕組みなしで避ける。
- **0.8.x(小課題、各 2 回)**: 0.8.0 は vanilla $0.194 / 42 秒に対し devaccel $0.213 / 82 秒、サンドボックスなしなら 46 秒。原因はサンドボックス denyRead の `~/**/.env`(Bash ごとに $HOME 190 万 inode を走査、`ls` 1 回 9.4 秒)。0.8.2 で vanilla $0.175 / 39 秒 対 devaccel $0.200 / 46 秒(コスト +14%、時間 +18%)、正確さは全条件満点。
- **含意**: 正確さの上積みは小課題では測れない。次は難課題・欠陥を誘う課題・並列シナリオで測る(fable 計画の中期)。

## D15. 検証は「人が見ていない境界」だけに置く(0.8.0)

- **決定**: ゲートは対話セッションで既定 off(`gate.mode`)、/batch の単位(worktree)では enforce(`gate.unit_mode`)。単位かどうかは「検査対象の木 ≠ 本体」で自動判定し、プロファイルの切替スイッチは作らない(設定 2 系統は 0.6 系のような退行源になる)。seed CLAUDE.md は進め方・検証を 6 行に(S/M の作法・ゲート説明・/batch・PR・Bash の注意を削除)。並列の作法は手動スキル `devaccel-batch` に移し、単位への指示に Bash の注意と devaccel-pr を必ず埋め込む(「単位が devaccel-pr を使うかは CLAUDE.md の 1 行頼み」を解消)。Codex 併用と observe→enforce の昇格を削除。
- **根拠**: D14。対話では小課題・罠つき難課題とも vanilla と正確さ同等で、時間だけ増えた(ベンチは enforce を強制していた)。価値が測れたのは無人の経路(単位内ゲート、振り分けの欠陥検出 8/8、land の衝突検出)。D4 の「observe で始めて enforce へ昇格」を撤回。
- **見直す条件**: 対話で vanilla 比コスト +5%・時間 +10% を超えたら残りの行もアブレーションで削る。単位ゲートの誤ブロックが続けば unit_mode を observe に。
